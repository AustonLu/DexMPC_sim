# dexmpc-sim v0.4.0 多核线性算子 SDK

本文是 per-operator 多核基线。连续 kernel 的驻留、两个独立策略开关和 kernel-level 周期统计见 [v0.4.1 连续驻留 Kernel SDK](v0.4.1_resident_kernel_sdk.md)；DOT 的 K-split 和固定归约见 [v0.4.2 多核 DOT SDK](v0.4.2_multicore_dot_sdk.md)。

适用版本：`dexmpc-sim 0.4.0`

## 1. 版本目标

v0.4.0 在 v0.3.0 无地址 Tensor/Operator API 上增加 TopChip 四个 MAC context 的可验证调度能力，覆盖：

- GEMM；
- GEMV；
- OUTER；
- SCALE/MUL；
- ADD。

只按独立输出行或连续输出元素切分，不沿 GEMM/GEMV 的 K 维切分。因此每个输出元素仍由一个 MAC 完成，FP16 乘加顺序与 v0.3.0 单核路径相同，多核结果必须逐 bit 一致。

## 2. 安装

在 Linux/Verilator 构建环境中：

```sh
python -m pip install --no-deps --force-reinstall \
  dist/dexmpc_sim-0.4.0-py3-none-linux_x86_64.whl

python -c 'import dexsim; print(dexsim.__version__)'
```

预期输出为 `0.4.0`。包仍自带 native runtime、RTL simulator model 和 LUT 数据；Algorithm 仓库不需要 include Verilator 头文件。

## 3. 高层用法

公开算子签名没有 core、context、SRAM 或地址参数：

```python
import dexsim

with dexsim.Device() as dev:
    a = dev.constant([[1.0, 2.0], [3.0, 4.0]])
    b = dev.constant([[0.5, -1.0], [2.0, 3.0]])
    c = dev.gemm(a, b)
    print(c.tolist())
```

`Program` 使用同一个 planner：

```python
program = dexsim.Program("linear")
a = program.input("a", (32, 8))
b = program.input("b", (8, 8))
c = program.gemm(a, b)
program.output(c)

with program.compile() as executable:
    result = executable.run(a=a_value, b=b_value)
```

## 4. execution policy

支持四种 policy：

| policy | 用途 |
|---|---|
| `auto` | 默认 production policy；只有 capability 已验证且完整 operator 周期实测有收益时才多核 |
| `single` | 强制真实硬件单核 baseline |
| `dual` | 诊断/实验用；请求 2 核，shape 不可切分时退到较少核 |
| `quad` | 诊断/实验用；请求 4 核，shape 不可切分时退到 2/1 核 |

```python
with dexsim.Device(execution_policy="single") as dev:
    ...

with program.compile(execution_policy="quad") as executable:
    ...
```

v0.4.0 的最终实测中，五类算子在“当前 D2D staging + gather”路径上都没有净周期收益，因此默认 `auto` 会选择硬件单核。`dual/quad` 保留用于正确性验证、RTL 性能研究以及未来加入片上搬运或持久副本后的重新标定，不能当作当前 production 加速开关。

## 5. 为什么不能直接共享 Global SRAM

四个 command context 都能编码 Global 地址，但多个 MAC 的 busy window 真正重叠时，并发 Global 访问会触发 RTL：

```text
Assertion failed: global SRAM contention
```

因此 v0.4.0 的多核执行流程是：

```text
logical Tensor/Op
  -> output-row/element partitions
  -> core1--3 input tiles staged to per-core Local/Temp
  -> one scheduled wave (at most one command per core)
  -> per-core Local/Temp outputs
  -> gather into one logical core0 Tensor
```

scratch allocator 会避开逻辑输出和已有 Local/Temp 输入。若每核 SRAM 放不下，`auto` 记录原因并执行真实硬件单核，不会回退 NumPy。

## 6. trace

每个线性算子的 eager trace 新增 `parallel`：

```python
entry = dev.trace()[-1]
parallel = entry["parallel"]

print(parallel["plan"])
print(parallel["commands"])
print(parallel["transfers"])
print(parallel["metrics"])
```

主要字段：

- `plan.requested_policy`：请求的 policy；
- `plan.core_count`：实际物理 core 数；
- `plan.partitions`：每核 start/size 和 core；
- `plan.reason`：选择或退回单核的原因；
- `commands`：每个 tile 的 core、command words 和 metadata；
- `transfers`：输入 staging 和输出 gather；
- `metrics.stage_*`：staging 周期和 D2D bytes；
- `metrics.run_*`：command submit/wait 与 MAC 执行；
- `metrics.gather_*`：gather 周期和 D2D bytes；
- `metrics.total_*`：完整 operator 成本；
- `metrics.wall_seconds`：cycle-accurate simulator 墙钟时间。

没有收益时的典型 plan：

```text
requested_policy: auto
core_count: 1
reason: below_measured_parallel_threshold
```

## 7. 低层 scheduled-wave API

普通 kernel 开发者不应直接使用该接口。验证工具可以显式构造一个 wave：

```python
with dexsim.Session(cores=(0, 1, 2, 3)) as session:
    run = session.run_scheduled([
        dexsim.ScheduledCommand(0, command0),
        dexsim.ScheduledCommand(1, command1),
    ])
```

约束：

- 一个 wave 最多 4 条命令；
- 每个 core 最多一条；
- core1--3 只接受 LA command；
- shared LUT/Reduce/ABS/DataLayout 只允许 core0；
- Local/Temp 的 `core=` 参数映射到各自物理 bank；
- 旧 `Session.run()` 默认 `(0,)` 和 C ABI 保持兼容。

## 8. 数值与边界

- GEMM/GEMV/OUTER 按输出行切分，行起点按 8 个 FP16 元素对齐；
- SCALE/ADD 按连续元素块切分；
- 支持不能整除 core 数的尾块；
- 4096 元素 SCALE/ADD 因 12-bit dimension 最大为 4095，会在单核路径下降为两个顺序 hardware command；
- 多核输出不放在共享 Global；
- `auto` 放置失败或无收益时仍执行硬件单核；
- 不存在 silent NumPy fallback。

## 9. 当前性能结论

20 个代表性 shape、60 条 1/2/4-core 记录表明，MAC-only `run` 阶段确实能并行，但 D2D staging/gather 主导总成本。最高观测到：

| 算子 | MAC-only 最佳 speedup | 完整 operator 是否有净收益 |
|---|---:|---|
| GEMM | 2.82x | 否 |
| GEMV | 3.15x | 否 |
| OUTER | 2.15x | 否 |
| SCALE | 12.36x | 否 |
| ADD | 15.87x | 否 |

因此 v0.4.0 不把诊断多核结果包装成 production 加速。要获得净收益，下一步应先增加片上跨 bank 搬运、broadcast 或可由 allocator 管理的持久 per-core replicas，再重新执行同一 benchmark；仅调整 Python core 阈值不能解决数据搬运瓶颈。
