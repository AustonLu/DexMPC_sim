# dexmpc-sim v0.4.1 连续驻留 Kernel SDK：原理、安装与使用

适用版本：`dexmpc-sim 0.4.1`

## 1. 版本目标

v0.4.1 在 v0.4.0 的 1/2/4 核线性算子后端之上增加 Program 级连续驻留调度。开发者仍然显式编写由哪些 FP16 硬件算子组成 kernel；SDK 负责地址分配、输出空间切分、每核 command 生成、依赖保持和数据搬运。

本版本解决的是连续算子之间的重复搬运：线性算子产生的 shard 可以留在对应 core 的 Local/Temp SRAM，后续算子直接消费；只有最终输出或共享引擎边界才 materialize 到 core0。它不是任意 Python/CasADi 源码编译器，也不替开发者判断公式中的精度边界。

## 2. 软件层级

```text
MPC 数学公式和 FP16 边界                 Algorithm / kernel 开发者
  -> 显式 Program 算子图                 dexsim.Program
  -> 生命周期、SRAM 和 residency 分析    CompiledProgram
  -> 1/2/4 核输出空间切分                parallel planner
  -> shard forwarding / replica reuse    resident executor
  -> 96-bit command 和 D2D 事务           Session
  -> cycle-accurate RTL                   Verilator TopChip
```

普通软件开发者不指定 SRAM 地址、bank、core ID、分块起点或 command word。低层 `Session` 和 command builder 仍保留给硬件验证和故障定位。

## 4. 两个独立控制开关

`Program.compile()` 的两个参数彼此独立：

```python
compiled = program.compile(
    execution_policy="quad",
    residency_policy="on",
)
```

`execution_policy` 控制允许使用多少 MAC core：

| 值 | 含义 |
|---|---|
| `single` | 固定 core0；真实硬件单核基线 |
| `dual` | 请求 2 核；shape 不能合法切分时退到 1 核 |
| `quad` | 请求 4 核；shape 不能合法切分时退到 2/1 核 |
| `auto` | 生产策略；只采用已经由完整周期验证为有收益的核数 |

`residency_policy` 控制是否消除连续算子之间的搬运：

| 值 | 含义 |
|---|---|
| `off` | 关闭；每个多核算子独立 stage、run、gather，等价 v0.4.0 |
| `on` | 强制尝试 Program 级驻留；不合法时记录原因并走真实硬件 fallback |
| `auto` | 由 SDK 根据核数、可复用边和已验证性能 Gate 决定 |

因此可直接构造四种诊断组合：单核、双核无驻留、双核驻留、四核无驻留、四核驻留。`single/on` 不会伪造驻留收益，因为单核没有跨核 shard；`auto/on` 和 `auto/auto` 在没有通过性能 Gate 时都保守使用单核。强制实验驻留路径应明确写 `dual/on` 或 `quad/on`。

可用 `compiled.execution_config` 和运行后的 `result.trace.residency["decision"]` 检查请求值、实际值和选择原因。

## 5. 编写连续 Kernel

```python
import dexsim

program = dexsim.Program("affine_chain")
x = program.input("x", (32, 8))
w = program.constant("w", [[0.125] * 8 for _ in range(8)])
bias = program.constant("bias", [[0.25] * 8 for _ in range(32)])

h = program.gemm(x, w)
scaled = program.scale(h, 0.75)
y = program.add(scaled, bias)
program.output(y)

with program.compile(
    execution_policy="quad",
    residency_policy="on",
) as kernel:
    result = kernel.run(x=[[0.5] * 8 for _ in range(32)])
    y_fp16 = result.outputs[y.name]
    y_bits = result.output_bits[y.name]
```

同一个 `CompiledProgram` 应重复调用 `run()`，不要每个 MPC stage 重新 compile。常量在 compile 时上传一次；v0.4.1 还会在同一个 compiled session 内复用已建立的 per-core 常量副本。

## 6. 已实现的避免搬运规则

v0.4.1 对 `GEMM/GEMV/OUTER/SCALE/ADD` 组成的连续线性子图实现：

1. 只读输入和常量的 per-core replica 复用；
2. producer 输出 shard 直接转发给同 core consumer；
3. 根据直接 consumer 选择兼容的 2/4 核 partition；
4. row-sharded 和 element-sharded layout 的继承；
5. 基于 Program last-use 的 Local/Temp SRAM 区间复用；
6. 只在 Program 输出和 barrier 处一次性 materialize；
7. 不变常量副本跨多次 `run()` 保留。

以下算子在 v0.4.1 中是 core0/shared-engine barrier：`SIN/COS/SOFTPLUS`、`ABS`、`ADD_REDUCE/COMPARE_REDUCE`、`ASSEMBLE/TRANSPOSE` 和 `DOT`。进入 barrier 前，所需 resident tensor 会显式 materialize；barrier 之后的线性子图可以重新分块和驻留。

这类优化常被统称为 operator fusion，但 v0.4.1 没有把多个数学算子改写成一个新 opcode。更准确地说，它融合的是跨算子的 layout、生命周期和数据搬运 schedule；各算子的 FP16 执行顺序不变。

## 7. 正确性和 fallback

驻留路径和 `residency_policy="off"` 使用同一硬件算子与 FP16 顺序。最终输出必须逐 bit 一致。最终输出、显式列入 `Program.output()` 的中间值、shared-engine 输入都会被 materialize。

以下情况会回退：

- shape 不能按 FP16 word 边界切分；
- 计划实际只能使用一个 core；
- tensor 落入 Global SRAM，不能作为私有 resident shard；
- Local/Temp 容量不足或 consumer layout 不兼容。

回退仍执行 simulator 硬件 command，不使用 NumPy 代算。原因记录在 `parallel_plan.resident_fallback_reason` 和 residency events 中。显式请求 4 核只表示“最多使用 4 核”；硬件合法性和 SRAM 容量始终优先。

## 8. 周期和搬运统计

```python
metrics = result.trace.kernel_metrics
resident = result.trace.residency

print(metrics["total_cycles"])
print(metrics["compute_only_cycles"])
print(metrics["internal_transfer_cycles"])
print(resident["metrics"]["avoided_stage_bytes"])
```

| 字段 | 统计范围 |
|---|---|
| `total_cycles` | 输入上传、算子、内部搬运、最终 materialize 和输出读取 |
| `compute_only_cycles` | scheduled hardware command 的 run 阶段；线性链中即 MAC core 计算周期 |
| `internal_transfer_cycles` | per-core staging 和中间 materialize |
| `input_upload_cycles` | host/core0 kernel 输入写入 |
| `output_materialize_cycles` | resident 最终 shard 汇集到 core0 |
| `output_download_cycles` | 最终 FP16 bits 读取 |

`trace.residency` 还包含每次 `resident_stage`、`materialize`、复用区域、延迟 gather、常量 replica hit 和 fallback。性能结论必须同时报告 `total_cycles` 与 `compute_only_cycles`：后者有收益不等于完整 kernel 有收益。

## 9. Kernel 开发者仍需负责的内容

SDK 不会从任意 MPC 源码自动发现硬件子图。接入新算法时仍需：

1. 从数学公式确定哪些值可按 FP16 计算；
2. 把该子图人工表达为 `Program` 的算子和依赖关系；
3. 明确 FP64/host、shared-engine 和状态更新边界；
4. 用 software golden、FP16 bit reference 和任务级 shadow 验证误差；
5. 用真实 shape 测量单核、无驻留多核、驻留多核的完整周期；
6. 只有端到端收益稳定通过 Gate 后才采用 `auto` production policy。

多核切分、核数退化、地址分配、replica、SRAM 生命周期和 command 编码属于 SDK，不应在 Algorithm kernel 中重复实现。

## 11. v0.4.1 实测策略

M6.2 最终用 4 个 shape、4 个 chain depth 和 5 种策略完成 80 条 cycle-accurate 记录，所有输出逐 bit 一致。稳态结果如下：

| 策略 | compute-only 几何平均 | compute >=1.05x | 片上含必要搬运几何平均 | 完整 kernel 几何平均 | residency 相对同核 off |
|---|---:|---:|---:|---:|---:|
| `dual/off` | 1.123x | 8/16 | 0.110x | 0.218x | - |
| `dual/on` | 1.123x | 8/16 | 0.438x | 0.656x | 3.013x |
| `quad/off` | 0.855x | 8/16 | 0.071x | 0.148x | - |
| `quad/on` | 0.984x | 8/16 | 0.332x | 0.543x | 3.667x |

“片上含必要搬运”排除 Program 输入上传和最终输出下载，但保留 per-core 输入分发与最终 shard materialize。该口径和完整 kernel 口径均为 0/16 case 达到 1.05x，因此 v0.4.1 的 production `auto` 保持单核。

显式 `dual/on`、`quad/on` 仍有两个用途：验证多核 bit-exact correctness，以及研究更大/更高算术强度 kernel 或后续片上互连优化。不得只引用 compute-only 数字宣称当前端到端加速。
